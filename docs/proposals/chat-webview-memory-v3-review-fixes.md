# V3 未提交改动审查修复计划

日期：2026-09-08。状态：七项修复及追加退订修复已完成；全模块门禁分段通过，生产 SDK/UI 与产物健康检查通过。

本计划覆盖本次代码审查确认的七项缺陷，承接 [V3 实施计划](chat-webview-memory-v3.md)。
此前完整构建通过是历史验证事实，不能作为下述修复已经完成的证据。

## 目标与固定边界

- 保留 `509f197` 的 JavaFX 布局、CSS 令牌、控件样式与交互语言；不重新设计聊天或设置中心。
- 保留 Desktop → SDK → App Server，14 个模块、Protocol v3、data-v6 和既有调度、持久化及隔离体系。
- 不升级依赖，不恢复旧 Runtime，不新增数据库、后台服务或通用状态管理框架。
- 优先使用现有 RPC、DTO 和存储历史能力；不得修改历史 SQL migration 或批量改写用户记忆。
- 不把有界摘要伪造成完整 Item，不用页面状态替代服务端权限、Turn 状态或 revision 校验。
- 遵守根 AGENTS.md 和 coding-style：中文 Javadoc，说明并发、取消、资源归属和事务不变量。
- 保留用户已有未提交修改；修复过程中不自动提交、不降低门禁、不调用付费模型。

## 七项修复设计

### R1：会话导航与运行状态解绑，P1

涉及 DesktopPresenter、DesktopTurnStreamCoordinator、DesktopStateProjection、DesktopTranscriptHistory。

1. 同一会话的重复选择应幂等，不释放正在使用的订阅或清空当前运行状态。
2. 真正切换会话或工作区时，在一次 UI 状态转换中更新选择、清空旧会话的活动状态及忙碌标记。
   停止展示订阅不等于取消服务端 Turn，不发送额外 start/cancel 命令。
3. 用导航代次、连接代次、ThreadId 和 TurnId 隔离迟到的启动结果、历史读取、订阅与终态回调。
   旧会话完成不能修改新会话的输入、审批或忙碌状态。
4. 返回会话时，使用已知运行上下文或最近权威历史中的 TurnId，经现有 `turn/read` 复核所属 Thread 和状态。
   非终态恢复观察，终态恢复输入；不假设存在当前 SDK 没有的 `turn/list`，不重启模型调用。
5. 不仅修改按钮 disable 条件；状态层、发送前校验和停止入口必须一致。
6. 退订只撤销该订阅的日志监听，不中断正在借用共享 RPC 连接发送的线程，避免关闭其他查询所用的 UDS。
   使用关闭标记与唤醒协作退出；已在途发送仍受原五秒硬超时约束。覆盖退订恰逢写帧后同一连接继续查询。

验收：A 正在生成时切到 B 可正常操作；返回 A 能继续观察或正确显示完成；重复选择 A 不中断输出；
A 的迟到 start/终态不污染 B；切换工作区、断线重连、取消及旧服务端降级路径均保持正确。

### R2：恢复结构化历史摘要，P2

涉及 ItemHistoryRepository、历史摘要投影、ChatSurface、原生简版及其测试。

1. 按已知 schema 为工具调用、工具结果、审批及错误生成明确的有界摘要，至少保留工具名、成功/失败状态、
   错误码、原因及必要的执行结果信息；未知 schema 明确显示类型及受限说明。
2. Desktop 按类别恢复既有标题与样式，原生简版和 WebView 使用相同的语义摘要。
3. 保持摘要 4096 UTF-16 单位、Unicode 边界及整个分页响应预算；超过预算明确标记截断。
   不将大 payload 整包拉回 Desktop，也不把非消息伪造成 MessageContent 引用。
4. 优先保持 ItemHistoryEntry 和现有 RPC 形状不变；投影在 Server 完成，不让 Server 依赖 Client 格式化器。
   本项恢复可读摘要，不增加任意结构化 payload 查看器。

验收：真实 H2 写入工具成功/失败、审批、Core Error、Coding 结果及未知记录后，history 返回有意义的摘要；
首屏、历史分页、完成刷新、重连和原生简版均能读到原因；长文本、多字节字符与响应大小限制仍通过。

### R3：自动刷新不得吞掉草稿，P2

涉及 ViewSchemaSettingsPage、ViewSchemaFeedbackPane、ViewRenderSession 和表单交互测试。

1. 将同 schema 的自动对账与用户主动加载区分：自动查询可在后台进行，不必显示整页加载遮罩。
2. 发起读取时记录页面代次、草稿修改代次和请求用途；响应到达时重新检查，不能只在请求发出前检查 dirty。
3. 若读取期间产生新编辑，保留原表单、输入值和焦点，不调用会重建表单的 apply；记录“服务端有更新”，
   继续复用现有保留草稿/明确重载交互。无变化的响应不重建原生表单。
4. 主动加载及提交中的遮罩需管理底层键盘编辑，不能仅挡住鼠标；成功、失败、取消和离页都恢复控件状态。
5. 不缓存或自动重放旧业务命令；用户保存时仍接受服务端 revision 冲突校验。

验收：可控 Future 阻住自动读取，在原有焦点上发送真实 JavaFX 键盘事件，返回响应后文字、dirty、焦点仍保留；
覆盖提交失败、主动刷新、上传、连续事件、离页和工作区切换；无编辑状态仍能自动更新任务和图谱。

### R4：冲突参与者使用统一语义规则，P2

涉及 MemoryLearningRules、MemorySemantics、普通提案和后台学习提交路径。

1. 在扩展内部统一冲突参与者筛选：当前未删除记录、相同作用域、满足既有标签关系且语义状态为 ACTIVE。
2. 候选分类与冲突注册使用同一份参与者快照，避免一处过滤、另一处重新纳入 SUPERSEDED。
3. ACTIVE、SUPERSEDED、时间有效范围和人工条件分别处理；不把暂时不在有效时间内等同于已被替代。
4. 已有 PENDING 冲突不静默改写参与者；过时冲突可明确关闭，采用新事实时按当前记录重新审查。
   保持 Workspace head、各参与者 revision 和事务内校验。

验收：北京→上海→杭州连续两次替换成功；普通提案与后台学习采用一致规则；并存、合并、跨作用域、
多参与者以及另一个冲突先替代参与者的场景，都不会复活旧记忆或修改过时参与者集合。

### R5：删除与旧冲突恢复闭环，P2

涉及 MemoryCommandHandler、MemorySemantics、MemoryV3Management、存储历史读取及冲突表单。

1. 新的 tombstone 操作在同一事务中检查 PENDING 冲突引用：存在引用时阻止删除，并明确提示先处理冲突。
   不把删除一条记忆解释为批量拒绝候选，检查与删除之间不能留下并发空窗。
2. 为已存在的异常记录增加内部参与者快照，优先读取当前记录；不存在时通过现有 `history()` 分页查找最新历史。
   墓碑使用 DocumentRevision.revision，不能使用 payload 内删除前的 Memory.revision。
3. 冲突编辑器展示参与者已删除/已替代及可用历史正文，继续通过现有 expectedMemoryRevisions 传递版本。
4. KEEP_EXISTING 允许基于当前墓碑或 SUPERSEDED 版本拒绝候选、关闭冲突；不恢复或重新激活任何记忆。
   REPLACE/MERGE/COEXIST 仍要求可裁决的当前 ACTIVE 参与者。
5. 保持 conflict revision、Workspace head、完整参与者键集合及每项当前 revision 校验。
   真正无任何历史的损坏记录明确失败，不能伪造版本号。
6. 旧数据通过正常页面读取和用户明确决议恢复；不新增启动时清理、SQL 补丁或静默批量迁移。

验收：新删除被正确保护；已有墓碑冲突可打开并明确关闭；超过一页历史仍取到正确墓碑版本；
读取后恢复、删除、替换或修改参与者时，旧裁决 CAS 失败并保留草稿；重复关闭幂等，重启后状态一致。

### R6：学习配置完整往返，P2

涉及 MemoryV3Management、学习 ViewSchema、DesktopExtensionCoordinator、ViewCommandBindingResolver。

1. 回显持久化的 approvalPolicy、reasoning；默认值只用于尚未创建的配置。
2. 保存的 Role、Provider 和 PermissionProfile 按精确 ID＋revision 与权威目录匹配，恢复对应选择。
   引用已删除、版本失效或尚未加载到时显示原引用及原因，不替换为首行或 latest。
3. 用户显式选择优先于初始回显；有效的 SINGLE 选择在重载时保留，明确取消选择不会被自动恢复。
4. 不把保存的 role/provider/permissionProfile 直接放入目录同名 values，避免覆盖 selectedRows 的新选择；
   不改变其他页面现有 values 优先的命令绑定规则，不在通用 Renderer 写 Memory 专用逻辑。
5. 当前 ViewQueryResult 没有直接的初选返回字段，因此初选传递先作为契约小项落地：使用受限、可选、版本化的
   声明式初选元数据，明确来源、键、精确版本、优先级和单次初始化语义，并验证成员确实存在于已加载目录。
   优先沿用现有 values 容器，不新增 RPC；缺少元数据时行为保持兼容，不依赖未经定义的特殊键猜测。
6. 元数据只影响展示选择，不授予能力；保存仍由服务器复核配置、权限及 definition revision。

验收：EVERY_CALL/HIGH 保存→重开→只改启停→保存后原值不变；多目录项恢复精确选择；重新选择后保存使用新值；
取消选择、失效 revision、目录分页、并发更新、旧服务端无初选元数据及其他自动化页面均不回退到错误默认值。

### R7：续租归属绑定文档版本，P2

涉及 DocumentPreviewPane、DocumentPreviewLoader 及生命周期测试。

1. 用明确的续租请求身份绑定 epoch、handleId 和请求代次，替代只判断一个共享 renewing 标志。
2. 相对导航开始即释放旧续租的页面归属；导航读取期间不为即将释放的父句柄启动新的续租。
3. 接收子文档时建立该版本自己的续租状态；旧成功/失败回调既不能阻塞新续租，也不能将 version 改回父版本。
4. 继续保持可见时续租、隐藏停止、关闭及撤权释放；不能通过延长租约或忽略失效通知掩盖竞争条件。

验收：父续租未完成→打开子文档→父响应迟到后子文档继续续租；资源解析与续租反向完成；
连续相对导航、失败、关闭、撤权、隐藏/显示及重连均没有句柄泄漏或旧正文重现。
使用可控 Future 和时间推进完成竞争场景，不用五分钟固定等待代替确定性测试。

## 整体验收与交付

1. 先运行相关模块的定向回归，再执行 `mvn spotless:apply` 并检查实际 diff。
2. 执行 `mvn spotless:check checkstyle:check` 及全仓 `mvn clean verify`，使用原覆盖率、架构、依赖和 Golden 门禁。
   如仍需临时 Maven Central settings，只使用项目外临时文件，不修改全局配置。
3. 更新维护型 UI 重放，加入生成中导航、结构化错误/工具结果、刷新中输入、精确配置回显及相对导航续租场景。
   使用真实生产 FXML / Presenter → SDK → App Server、临时 H2/工作区和固定模型；不读取用户真实数据。
4. UI 至少复核 Emerald/标准/100% 和 Midnight/紧凑/120% 两组：保持原主题、布局、按钮位置和交互文案体系；
   新增内容只恢复缺失信息和明确失败原因。54 张既有 appearance Golden 仍独立运行，不能替代新场景验收。
5. 运行打包产物健康检查。通过的测试、条件跳过、失败和未验证平台分别记录，不预设新的总测试数。
6. 归档修复前后场景、原始截图、日志和摘要；更新验收矩阵及相关契约说明，执行 `git diff --check`。
7. 对七项分别标记已修复/验证依据/剩余限制，再做独立复审；不自动创建提交。

本轮不顺带修后台任务列表裁切、WebKit 彩色 emoji、跨平台发行或大图性能问题。它们继续作为独立已知限制，
不能因这七项修复完成就标记通过。Windows/Linux、输入法、DPI 及安装签名仍需对应环境的真实回执。
