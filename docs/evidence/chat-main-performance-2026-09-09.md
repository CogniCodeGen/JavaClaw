# 主聊天性能与交互实现记录

日期：2026-09-09。环境：macOS arm64、JDK 25、JavaFX 26.0.2。

## 实现与边界

本轮在现有浅暖底色、绿色强调、圆角及左导航体系内，缩小消息和输入区留白，右侧待处理区改为按需展开。
输入框初始约 60 逻辑像素，增长上限 240；空反馈行和隐藏备用列表不参与布局。
待处理提醒按请求身份去重，文档阅读不会被新审批切走，窄窗口两侧区域互斥且保留导航偏好。
Enter 换行，Ctrl 或 Command + Enter 发送；组合输入期间不发送，Escape 关闭当前弹层或面板并恢复焦点。

聊天内部展示协议改为消息增量，服务端协议、SDK 公共接口和业务回调语义不变。
实际提交到 DOM 的版本决定下一次增量与引用映射；两帧显示确认只控制背压，不能提前使可见链接失效。
切换会话、宿主恢复或基线失配使用完整快照。文档及图谱的旧载荷和动作门禁保留。
流式普通文本原位追加，Markdown 更新保留消息容器；仅测量变化节点，高度缓存包含真实间距并随外观变化失效。
代码高亮限制在可见区域，分帧执行并使用有界缓存。空闲宿主不再维持每 50ms 的轮询。

确定性传输回归使用 500 行：499 行稳定正文、1 行变化正文；合并七次后台更新后仍以实际提交版本生成补丁。
该夹具完整 JSON 超过 100,000 字符，补丁小于 300 字符且只含变化行。
这说明消除了重复传输历史正文的工作量，不代表每一种回复长度都能获得相同比例的耗时改善。

## 测量方法

回放入口为 `scripts/replay-chat-performance.py`。夹具使用生产 `main.fxml`、Controller、Presenter、SDK 和真实 WebView，
通过内存 RPC 提供数据，直接以 `com.javaclaw.desktop` 命名模块启动，保持 IDEA 的模块启动路径。
不读取用户聊天、不创建 Turn、不调用模型、不写用户偏好。
修改前的生产编译产物在开始编辑前单独保存，对应 `19f391b45e38e91f25715f4051a9b30f268d0f9f`；两侧使用相同回放源码。

每个场景预热 3 秒，随后独立测量 2.5 秒空闲 CPU；之后依次进行 30 次中文字符事件输入和 90 次原生滚动事件。
压力场景同时提供 20/60Hz 流式通知及约 32K 字符的回复前缀。每次输入等待 Scene 布局完成，必须完整保留 30 个字符。
500 条历史用于逻辑缓存上限压力，夹具一次提供完整缓存，不将其当成真实服务的单页大小。
跨窗口场景另外检查确实更换至少两个虚拟窗口；挂载上限仍为 128 条。

输入指标是 JavaFX 事件入队至 Scene 布局完成的 P95，Pulse 是活动期间 JavaFX 的回调间隔，
二者均不是物理键盘到屏幕的光学延迟。CPU 百分比以一个核心为 100%，不等于整机 CPU 百分比。
JFR 使用 profile 设置，按 JSON 中 idle/input/scroll 的时间范围过滤启动、预热和结束截图。
持续测量期间不截图；截图只验证最终内容和布局，避免像素缓冲分配污染结论。

## 同机前后对照

原始数据：[修改前](chat-main-performance-2026-09-09/baseline-results.json)、
[修改后](chat-main-performance-2026-09-09/current-results.json)。两侧均为单轮 6 场景回放，未在测量期间运行 Maven。
表中 CPU 包括输入、滚动及同时进行的流式处理，以单核 100% 计。

| 场景 | 输入 P95 前→后（ms） | 最大 Pulse 间隔前→后（ms） | 活动 CPU 前→后 |
| --- | ---: | ---: | ---: |
| 2 条消息，回复结束 | 10.77 → 9.30 | 17.98 → 17.41 | 43.4% → 30.7% |
| 32 条 Markdown，20Hz | 20.63 → 16.24 | 17.95 → 27.71 | 85.1% → 79.3% |
| 500 条消息，20Hz | 20.18 → 18.71 | 24.57 → 17.58 | 71.6% → 66.2% |
| 32 条多代码块，60Hz | 16.40 → 20.29 | 25.09 → 25.11 | 72.6% → 71.6% |
| 500 条消息，60Hz | 17.89 → 18.95 | 28.26 → 25.06 | 73.8% → 75.2% |
| 500 条消息，跨虚拟窗口滚动 | 9.36 → 9.73 | 16.66 → 16.81 | 46.1% → 48.3% |

两侧各 180 次输入完整保留，没有超过 100ms 的活动 Pulse 间隔。新版短对话低于 50ms，所有压力场景低于 100ms。
跨窗口场景记录到旧版 3 个、新版 5 个挂载窗口；滚动锚点是否漂移另外由原生滚动及 DOM 回归断言检查，
不从窗口数量或滚动距离推断流畅性。静态短对话的单核空闲 CPU 为 11.3% → 14.9%，未下降。

这些数据表明最终版本达到本机事件到布局的响应预算，但并非每项指标都改善：多代码块、500 条 60Hz 和跨窗
场景的输入 P95 上升，部分空闲及活动 CPU 也上升。新旧虚拟窗口挂载范围、实际换行和绘制面积不同；
合成 RPC 与 Desktop 同进程，CPU 还含夹具的编解码工作，不能等同真实独立 App Server 下的 Desktop CPU。
前面的迭代回放也出现过部分场景反向波动，因此不把单次测量解释为稳定提升幅度。
确定性收益是减少重复历史传输、整块 DOM 重建和空闲宿主轮询，不能据此宣称原先卡顿已彻底消失。

| 短对话输入阶段 | P95 前→后（ms） | 最大值前→后（ms） |

| Layout Pass | 1.721 → 0.988 | 2.190 → 2.244 |

空闲两侧仍各有约 300 次很短的 CSS/Layout 阶段；宿主停止轮询不等于 JavaFX 运行时完全没有 Pulse。

## 验证范围与限制

自动化回归覆盖增量跳版本、基线失配、延迟确认期间点击、引用目标变化、会话切换、恢复、历史分页、文档和图谱。
主聊天 Scene 检查 9 种主题 × 3 种密度 × 4 种字号 × 2 种尺寸，共 216 组组合，
每组包含短草稿闭栏与长草稿开栏，另检查长模型名、待处理提醒、输入焦点和快捷键。

本轮没有取得用户原先的真实短对话卡顿样本；旧版与新版夹具均不能重现持续明显卡顿，
因此不能认定已查明或消除该环境中的全部根因，也不能把长历史结果替代短对话验收。
真实中文输入法候选窗、物理鼠标/触控板、Windows/Linux 尚未验证。
128 条 DOM 虚拟窗口以外的节点会卸载，跨出窗口的超长拖选和被卸载代码块的横向滚动位置不作跨窗口保存保证。
