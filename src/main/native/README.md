# Desktop native ABI and Java bindings

`desktop_bridge.h` is the versioned C ABI shared by the Windows and macOS
libraries. Java calls it through sources generated by OpenJDK jextract 25.
The generated sources are checked in, so a normal Maven build does not need
jextract, a C compiler, or a native library.

ABI version 2 introduced a nonzero process instance ID in each discovered window.
It comes from the process creation time (Windows `FILETIME`, macOS start time
in microseconds). The target ID includes this value, and `jc_desktop_open`
checks it again before starting capture. If a PID and window ID are reused
while the user is granting access, opening fails and the target must be
discovered and approved again. Processes whose instance cannot be read are
not listed.

ABI version 3 adds an explicit `jc_desktop_request_permissions` entry point for
the settings switch. Status checks call `jc_desktop_probe` and never prompt.
On macOS the request uses the system Screen Recording and Accessibility APIs;
the Accessibility prompt is asynchronous, so settings must allow a fresh status
check after the user grants it. Windows has no single permission dialog for
WGC and UI Automation; the request reports available capabilities instead.

ABI version 4 adds a pixel-content revision to frames and actions, a bounded
`jc_desktop_list_elements` accessibility summary, and explicit foreground
prepare/restore calls. Element records contain role, label, rectangle and
supported action bits; input field values are never exported. The Java service
binds each action to a committed observation ID and checks its window generation
and content revision before calling the native bridge. `UNSUPPORTED` means no
input was dispatched. The generated Java bindings and both platform libraries
must be shipped together at the same ABI version.

ABI version 5 marks operating-system surfaces in each window's flags. This
classification comes from the native window owner, so a status-bar proxy cannot
be mistaken for the application named in its title. No structure layout changes.

ABI version 6 adds `JC_ACTION_ACCEPTED`: the platform accepted the complete
requested input, while the application's requested outcome remains unverified.
Successful AX/UIA calls, queued Windows messages, complete `SendInput` insertion,
and complete CoreGraphics posting return this status. API errors after dispatch,
partial sequences and lost results remain `UNKNOWN`. `VERIFIED` only indicates
a low-level control value or state was read back. Java receipts map both
`ACCEPTED` and `VERIFIED` to admission `ACCEPTED`, delivery `SENT`, and business
effect `UNKNOWN`; a new observation establishes the application outcome. An
`UNKNOWN` input requires observation and trusted reconciliation before further
input. Older clients could misread the new status as `FAILED`/`NOT_SENT`, so ABI
v5 libraries and clients must not be mixed with v6. Structure layouts are unchanged.

Optional additive extensions preserve the layouts introduced in ABI v5:
`jc_desktop_list_applications` reads installed application metadata without
launching or sending input. It returns a complete UTF-8 JSON catalog of up to
256 applications, with a maximum of 32768 bytes including the terminating NUL.
Each entry has `name`, `displayName`, `applicationId`, `launchName`, and bounded
aliases. `launchName` is the exact identifier accepted by this platform's launch
resolver; `applicationId` separately identifies the owning application.
`required_bytes` includes the NUL; a NULL buffer with capacity zero is a read-only
size probe. A short buffer returns -1 with empty output; no partial identity is
returned. `truncated` must remain visible to callers. macOS reads standard
Application bundle roots and localized metadata; Windows reads App Paths in both
registry views and unique, supported Start Menu shortcuts. Paths are not exposed.
Java loads the symbol dynamically. ABI-compatible libraries without this symbol report this
extension as unsupported while keeping their existing launch interface.

`jc_desktop_perform_element` accepts an opaque, nonzero element token from the
latest accessibility catalog. macOS retains that element's AX identity and
validates its process instance, window, role, actions, geometry and captured
target pixels before a single-left-click `AXPress`. A new catalog invalidates
old tokens; a missing or changed token returns `STALE_FRAME` without a coordinate
fallback. Changes outside the captured target region may be accepted. Once the
AX action is attempted, success returns `ACCEPTED` and an AX error returns
`UNKNOWN`; neither establishes the requested application outcome. Other gestures
retain the existing coordinate/platform path.
Java looks up this extension dynamically, so ABI-compatible libraries without the symbol
continue to use their existing input path. The additional symbols are deliberately
excluded from mandatory jextract wrappers, like the launch extension.

`jc_desktop_element_diagnostics` exposes bounded counters and native error codes
from the last catalog read, without field values or user text. Providers without
this optional extension return an empty diagnostic. The service carries the
diagnostic through observation admission and the agent's observation output.
macOS catalog collection uses work/time limits and reports truncation or AX read
failures; the output prioritizes actionable controls over layout containers.
For sparse trees, the provider can request an application's supported
`AXManualAccessibility` capability once per process instance, then wait for its
tree to populate. Transient errors before the enabling write permit bounded
capability re-probes with backoff; an attempted write is never repeated for that
process instance. It does not depend on application names or enable the
undocumented `AXEnhancedUserInterface` attribute.

`jc_desktop_launch_application` was introduced as an ABI v3 extension. The
current Java bridge requires ABI v6 for all desktop sessions and checks this
symbol before use. The function accepts
an exact installed application display name or bundle ID, never a path or
command, and returns the actual process ID on success. It can also return a
process ID with a nonzero status when launch succeeded but process verification
or foreground activation failed. A timeout does not prove that launch failed:
the caller must discover windows before retrying. Launch return codes -1 through
-4 reject admission before system dispatch and become trusted `NOT_SENT` results;
all other nonzero launch results, including -6, remain uncertain. Do not apply
this launch-specific interpretation to other ABI entry points. macOS resolves application
bundles through Launch Services, with a bounded exact-identity fallback in
`/Applications` and `~/Applications`, and uses `NSWorkspace` to launch or activate
them. Windows resolves an exact installed name from Start Menu shortcuts or an
executable name from registered App Paths, then uses `ShellExecuteExW`. Both
providers expose an optional read-only process application ID for recovery when
the window display name differs from the launch request.

To regenerate after changing the header, obtain the **OpenJDK jextract 25**
binary for the build host from [the OpenJDK jextract page](https://jdk.java.net/jextract/)
and use JDK 25:

```bash
JEXTRACT_BIN=/absolute/path/to/jextract src/main/native/generate-bindings.sh generate
JEXTRACT_BIN=/absolute/path/to/jextract src/main/native/generate-bindings.sh check
```

The argument file limits extraction to JavaClaw's own ABI; it excludes system
headers. Two deterministic normalizations are applied to jextract output:
its unused `C_LONG` constant becomes a platform-neutral `MemoryLayout` because
Windows uses a 32-bit C `long` and macOS uses a 64-bit C `long`; and its default
symbol lookup is replaced with the bridge's exact-path library lookup. The ABI
uses `int32_t` and `uint64_t`. Generated struct layouts and function wrappers
are otherwise unmodified. Review the generated Java diff and run the check
command whenever the header or jextract version changes.

The Java bridge creates a `SymbolLookup.libraryLookup` only for a verified
absolute path under `ApplicationHome/runtime/native/<platform>/`. It then uses
jextract's generated function wrappers. Generated code cannot select a library
from `PATH`, `java.library.path`, plugins, or the working directory. The source
checkout can use `target/native/<platform>/` for local development.

Build the platform libraries with `macos/build.sh` or `windows/build.ps1`.
Place the built library under the portable application's `runtime/native/`
directory before signing the distribution. The running application does not
download, compile, or extract a native library into a writable directory.
